# Architecture and source contracts

For installation, start with the [merchant guide](README.md).

## Surfaces

| Surface | Responsibility |
| --- | --- |
| `app.commerce.config.js` | App identity, business schema, installation and SaaS webhook subscriptions |
| `src/shared/config-schema.js` | Native admin fields and simple instructional descriptions |
| `scripts/create-payment-methods.js` | Idempotent OOPE registration/deactivation through associated Commerce |
| `create-session` | Public POST: masked cart capability, trusted totals, profile selection, idempotent Azupay request |
| `payment-status` | Public POST: signed receipt, provider reread; returns status only |
| `checkout-branding` | Public exact-origin POST: Commerce store-code lookup and explicit whitelist of effective checkout title/byline/logo fields |
| `validate-payment` | Adobe-authenticated required before-order validation |
| `filter-payment` | Adobe-authenticated availability filtering by store-scoped enablement/readiness |
| `capture-cart` | Adobe-authenticated quote-save callback for canonical SaaS cart binding |
| `reconcile` | Private Runtime action: verify persisted paid orders and offline invoice |
| `storefront/` | Same-tab hosted checkout/session recovery and GraphQL order completion |
| `storefront/eds.js` | Portable EDS slots/native-handler adapter; deployment URL from shopper-scoped OOPE GraphQL |
| `eds/installer.js` | AST-aware, preflight-checked installation into supported merchant checkout sources |

The checkout GraphQL after-hook changes only Azupay payment titles before native
model transformation; the payment detail slot renders its byline/images with DOM
text APIs. Branding does not change order/payment codes, validation, amounts or
provider credentials. Logo URLs are loaded as browser images, never fetched by
Runtime. Official AP+ marks require explicit merchant confirmation of usage
rights and are not bundled with this extension.

Generated App Management actions serve configuration, scope trees, association and
installation. Their authenticated worker-process registration is generated by
Adobe's library. No hand-maintained admin iframe or duplicate settings store is
needed.

## Trust boundaries

The browser cannot choose the API base URL, API key, client ID, amount, numeric
quote ID, receipt signature or trusted payment state. The masked cart ID is a
capability, just as it is for Commerce guest-cart APIs. Keep it private.

SaaS does not expose the guest-cart REST routes used by some on-premises examples.
The session action first verifies masked-cart access through the associated
Commerce GraphQL endpoint, using the current shopper's optional customer token
and explicit store-view code. It creates a server-generated random marker,
records it in App Builder State for five minutes, and saves it as a cart custom
attribute. A second marker save lets the authenticated quote-save callback read
the first committed marker. That callback binds the marker to the native quote
ID; the session action verifies the binding and marker again.

Server-side `carts/{numeric-id}` and totals reads determine price, currency, addresses, store
and internal quote ID. The signed receipt contains only quote/store/amount,
provider IDs, profile selection and expiry; no credentials or shopper bank data.
HMAC-SHA256 verification uses constant-time comparison.

Commerce order placement checks the **actual order** amount/currency/quote/store
against the signed receipt, then rereads Azupay over TLS. Receipt authenticity
alone is not settlement. Only exact `COMPLETE` state, exact amount and selected
rail succeed. Returned/expired/unknown states fail closed.

Runtime action `final` annotations protect bound deployment inputs from request
overrides. Required Commerce hooks use Adobe authentication. Provider API calls
have timeouts and reject redirects; browser origins, return origins and provider
checkout hosts have exact allowlists.

There is no provider callback endpoint in this version. Checkout polls on
explicit customer checks; the scheduled worker independently verifies persisted
orders. Polling is documented by Azupay and avoids inventing an undocumented
webhook signature scheme.

## Azupay API

Base URLs are hard-coded to:

```text
UAT:        https://api-uat.azupay.com.au/v1
Production: https://api.azupay.com.au/v1
```

Authentication is raw `Authorization: <SECR key>`, **not** `Bearer`.

Creation:

```text
POST /paymentRequest
{"PaymentRequest":{
  "clientId":"<selected profile>",
  "clientTransactionId":"commerce-<deterministic hash>",
  "paymentAmount":10.29,
  "paymentDescription":"Commerce checkout <quote>",
  "multiPayment":false,
  "paymentExpiryDatetime":"<ISO-8601>"
}}
```

Lookup uses `GET /paymentRequest?id=<URL-encoded request ID>`, not an invented
path-parameter route. Creation and lookup use the `PaymentRequest` and
`PaymentRequestStatus` envelopes. Hosted navigation uses the schema's
`PaymentRequest.checkoutUrl` and the documented `redirectURL` query parameter.

The scoped `checkoutPresentation` single selection defaults to `redirect` and
is validated before creating a provider request. The create-session response
supplies `redirect` or `modal`; saved sessions retain that selection across
configuration changes. Legacy sessions without it remain redirects.
Modal mode uses a native accessible dialog and Azupay's `type=iframe` URL,
without return/cancel navigation inside the frame. Exact provider origin and
iframe `event.source` are required for `PaymentRequest` message wakeups.
Messages never establish payment: the signed-receipt status action revalidates
the provider. Five-second polling stops after 60 checks or a verification error;
manual retry remains available. A verified modal payment closes the dialog but
retains the receipt until the shopper's final native order submission succeeds.
Closing or escaping the modal never cancels/recreates the provider request.

Azupay's PaymentRequest guide explicitly says repeated `clientTransactionId`
returns the existing request/status. The transaction ID hashes quote, store,
amount, environment and experience. The extension does not make a blind
second-charge retry or substitute a fresh ID after a timeout.

The hosted choice is configured on the client in Azupay Dashboard. Separate
profiles implement the requested Commerce admin selector without undocumented
`payToEnabled`/`paymentMethods` fields.

## Limits requiring product-specific follow-up

- One-off fixed AUD payments; Australian billing and shipping.
- Synchronous payment-before-order checkout, with manual paid-cart recovery.
- No automated refunds, recurring agreements, stored payer data, post-invoice
  returns, disputes or split invoicing.
- The authenticated quote-save subscription and shopper-scoped GraphQL access
  must work for both guest and logged-in carts in your ACCS tenant. Customer
  tokens are forwarded only to the associated Commerce GraphQL endpoint and
  are never stored in receipts, browser session records or App Builder State.
- The pending-order invoice scanner is bounded, not a high-volume event queue.
- Separate profile provisioning is an Azupay account/commercial dependency.
- The bundled installer supports Checkout drop-in 3.x and the boilerplate
  6.x-style source contracts. Other checkout layouts require manual integration
  using the same Azupay-owned adapter. Merchant publication is separate from App
  Builder deployment; no merchant domain or Runtime namespace is baked in.
